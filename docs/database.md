# База данных MVP

Схема: `backend/internal/migrations/001_migration.sql`, PostgreSQL 15+.
Это начальная миграция для новой базы. Если прежняя версия 001 уже применена,
изменение файла не обновит существующую базу: нужна отдельная ALTER-миграция.
Не удаляйте существующие данные ради повторного запуска 001.

## Что найдено в проекте

Python-файлы backend/frontend/ml пока пустые; действующих моделей, API,
импортера, Docker-конфигурации и механизма запуска миграций нет.
README описывает предполагаемую структуру, `index.html` — доску требований.
Поэтому изменения схемы сейчас не требуют переименований в коде приложения.
Численные цели с доски — продуктовые гипотезы, не измеренные свойства реализации.

В `ml/data/classification_classes` есть реальные исходные CSV:

| Файл | Наблюдения при проверке |
| --- | --- |
| `df_Uid_data_hack.csv` | 85 525 строк, 85 514 разных SYNTHETIC_U; один идентификатор имеет несколько разных профилей |
| `df_Uid_payment_hack.csv` | 1 380 585 строк, 1 380 568 направленных пар; 9 пар повторяются; 27 406 строк с одинаковыми плательщиком и получателем |
| `df_Fid_Uid_link_hack.csv` | 12 514 уникальных пар физлицо/организация |

В платежах встречаются 114 552 идентификатора компаний без основного профиля,
в связях с физлицами — 7 788 таких идентификаторов. Это отдельные множества,
их размеры нельзя складывать для получения общего количества компаний.
Названий компаний и ИНН в этих файлах нет.

В `ml/data/alfa-bank_materials_for_large_business` лежат 9 Markdown-материалов.
Есть ошибки OCR, старый обзор стали за 2021 год и расхождение даты в имени
одного файла с датой в тексте. Дату нельзя подставлять автоматически из имени
без проверки; неизвестная дата остаётся NULL. Не выдавайте старую позицию банка
за текущую.

## Таблицы и сценарий

| Таблица | Назначение |
| --- | --- |
| `organizations` | Профили и записи-заглушки для неизвестных контрагентов |
| `users` | Имя, должность и выбранная компания; пока без механизма аутентификации |
| `payment_flows` | Исходные направленные платежные наблюдения с суммой и количеством |
| `organization_relations` | Подтверждённые зависимости с типом, весом и основанием |
| `person_organization_links` | Обезличенные связи через физлиц |
| `sources` | Издатели и необязательная оценка их надёжности |
| `materials` | Общий корпус внешних новостей и аналитики банка |
| `material_entities` | Участники материалов, в том числе несопоставленные |
| `analysis_runs` | Запуск анализа, профиль компании на момент анализа и журнал шагов |
| `insights` | Вывод для компании и должности: факты, банк, AI, риски и действия |
| `insight_evidence` | Конкретный вывод, подтверждающий материал и точная цитата |

Пользователь выбирает компанию и должность. По профилю и графу отбираются
материалы. Анализ создаёт `analysis_runs`, фиксирует контекст и действия,
затем сохраняет один инсайт и его доказательства в транзакции и завершает запуск.
Для следующего инсайта создаётся следующий запуск. Неудачный запуск сохраняется
с `status = 'failed'`, временем окончания и описанием ошибки, даже без инсайта.
Пустая выдача может завершиться без инсайта.

Лента отбирается через `insights JOIN analysis_runs` по компании и должности.
Должность не даёт права доступа: backend должен отдельно проверять компанию
пользователя. Схема сама по себе не реализует RBAC и регистрацию с паролем.

## Правила импорта

1. Читать CSV с учётом BOM и фактического разделителя. Пустые значения → NULL,
   флаги `0.0`/`1.0` → BOOLEAN. Не заменять неизвестный признак на false.
2. До загрузки профилей выявить повторяющиеся SYNTHETIC_U. Для конфликтующих
   профилей сохранить исходные строки отдельно для разбора; нельзя молча
   выбирать последнюю строку или склеивать несовместимые признаки.
3. Создать организации для объединения всех идентификаторов трёх CSV.
   У заглушек заполнен только synthetic_u; интерфейс показывает его как название.
   Профиль позднее обновляется по synthetic_u, внутренний id сохраняется.
4. Общие признаки лежат в типизированных колонках. Остальные исходные поля
   организации сохраняются в `profile_data` с исходными именами, включая
   возраст, штат, собственность, стадию бизнеса, клиентский статус и прочие флаги.
   `FTS_COUNTRY_NAME` разбивается на страны по запятой с удалением пробелов.
   Единицы REVENUE_COMPANY и PAY_AMT нужно сверить с описанием данных;
   схема не задаёт им валюту, период или фиксированную связь друг с другом.
5. В `payment_flows` сохранять каждую строку с номером (с 1, без заголовка)
   и стабильной ссылкой на версию файла. Уникальность `(source_ref, source_row)`
   позволяет не вставлять одну строку повторно при повторном импорте.
   Исходный CSV содержит только объём и количество: даты и валюту не выдумывать.
   Повторяющиеся пары сначала проверить: нельзя считать дубли аддитивными
   и суммировать их автоматически без выяснения происхождения.
6. Связи по физлицам импортируются по паре SYNTHETIC_F / organization_id.
   Не трактовать их как доказательство владения или поставок.

## Новости и доказательства

Из текста достаточно извлекать summary, участников, отрасли и географию.
Заголовок, текст, дата публикации и ссылка приходят от парсера.
Масштаб, тональность, стадия процесса и отдельные даты события пока убраны.
`processing_status` отличает ещё не обработанный материал от обработанного
без найденных участников/тегов; ошибка парсинга/анализа хранится отдельно.

`materials.source_ref` — URL для статьи или относительный путь в репозитории
для локального Markdown. Уникальность ссылки защищает от повторного сбора
одного материала у источника, но не объединяет перепечатки разных издателей:
семантическая дедупликация остаётся задачей обработки.

Не сопоставлять реальные названия из новости с SYNTHETIC_U без подтверждённого
соответствия. В таком случае `material_entities.organization_id` остаётся NULL.
Для демо допустимы явно обозначенные синтетические названия/новости.

Надёжность хранится у источника. Это не вероятность истинности каждой статьи.
Уверенность в персональном выводе хранится отдельно в `insights.confidence`.
Наличие кредита не доказывает плавающую ставку, город регистрации не доказывает
географию всех операций, доля платежей не равна зависимости поставок.

`bank_view` заполняется только при наличии подходящей аналитики; иначе NULL.
Каждый показываемый блок должен иметь записи `insight_evidence` с claim и quote.
Приложение проверяет, что цитата есть в body, что источник позиции банка имеет
тип bank_analytics и что аналитика актуальна. SQL проверяет ссылки и типы,
но не смысл выводов. Сохранять инсайт и доказательства нужно одной транзакцией.

JSONB используется только там, где форма зависит от анализа:
`risks`, `opportunities`, `suggested_actions` — массивы строк;
`company_context` — снимок признаков и использованных путей графа;
`steps` — массив объектов с инструментом, временем, входом, результатом и ошибкой.
Не записывать в журнал ключи API, пароли и скрытые рассуждения модели.
Для воспроизводимости сохраняются модель и версия пайплайна.

## Граф

Обход платежей использует индексы payer/beneficiary в обоих направлениях,
но сохраняет смысл направления денег. Для зависимости `A → B` в
organization_relations A зависит от B; распространение эффекта от B к A
идёт по обратной связи. Рёбра разных типов нельзя считать эквивалентными.

Глубина 3–4, запрет повторного посещения вершины внутри пути, исключение
платежей самим себе, лимит соседей и порог веса задаются алгоритмом обхода.
Фактические использованные пути, происхождение рёбер и веса фиксируются
в `analysis_runs.company_context`. Ослабление по глубине — эвристика ранжирования,
не оценка финансового ущерба.

## Проверка

На отдельной пустой тестовой базе:

```sh
psql -X -v ON_ERROR_STOP=1 -d alfahack_test -f backend/internal/migrations/001_migration.sql
psql -X -v ON_ERROR_STOP=1 -d alfahack_test -f backend/tests/schema_smoke.sql
```

Smoke-проверка откатывает свои фикстуры; миграция создаёт схему.
Она проверяет неполный профиль, повторяющиеся пары платежей, ограничения,
поиск связи через два перехода и персональный инсайт с новостью и аналитикой банка.
Чаты, уведомления, обратная связь и векторный индекс пока не добавлены:
их можно внести следующими миграциями при реализации соответствующих сценариев.
