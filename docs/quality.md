# Контроль качества контента и моделей

## Сводка эксплуатации

После запуска анализа агрегированные метрики можно получить из PostgreSQL:

```sh
uv run python -m backend.manage quality-report --days 30
```

Команда не выводит текст новостей, имена, email, идентификаторы компаний или
LLM-промпты. Она показывает статусы заданий, число обработанных/созданных/
пропущенных/ошибочных материалов, режим генерации, покрытие цитат и банковской
позицией, статус верификатора и распределение оценок пользователей.

## Метрики и действия

| Метрика | Как читать | Действие при отклонении |
| --- | --- | --- |
| `failed / submitted` | Ошибки загрузки или обработки материалов | Разобрать коды ошибок по источнику; отключить повреждённую ленту до исправления |
| `skipped / submitted` | Доля материалов без поддерживаемых факторов или достаточных данных | Выборочно проверить пропуски; расширять словарь только после ручной разметки |
| `verification.pass_rate` | Доля успешных проверок среди всех попыток, включая неудачные и повторные | Целевое значение 100%; любой спад блокирует релиз до разбора |
| `citation_coverage` | Доля инсайтов с сохранёнными ссылками на подтверждения | Целевое значение 100%; отсутствие цитаты считается дефектом |
| `bank_view_rate` | Доля инсайтов с подходящей датированной аналитикой банка | Интерпретировать вместе с доступностью материалов, не повышать искусственно генерацией |
| `useful / (useful + not_useful)` | Пользовательская оценка среди содержательных ответов | Сигнал для экспертной выборки, не автоматическое доказательство качества |
| `already_known` | Доля повторно известных пользователю событий | Проверить дедупликацию, ранжирование и глубину истории |
| `generation_modes` | Сколько результатов создано live-моделью и правилами | Сверить с разрешённой конфигурацией и ожидаемым режимом выпуска |

## Регулярный процесс

1. Перед каждым выпуском прогонять синтетический end-to-end сценарий и набор
   новостей, не использовавшихся при разработке. Хранить ожидаемые факты,
   направления факторов, обязательные источники и недопустимые выводы отдельно
   от промпта.
2. Еженедельно проверять случайную выборку не менее 20 новых результатов либо
   все результаты, если их меньше. Размечать точность фактов, правильность
   персонализации, актуальность банковской позиции, качество действия и точность
   цитаты двумя экспертами; разногласия разрешать совместно.
3. Сопоставлять экспертную оценку с полезностью пользователей по ролям и
   отраслям. Не менять веса ранжирования на малой выборке: для изменения нужно
   не менее 50 размеченных наблюдений на целевую группу и повторная проверка на
   отложенных материалах.
4. При любой неверной цитате, неподтверждённом факте, утечке чувствительного
   контекста или выборе модели вне списка приостанавливать live-режим, сохранять
   безопасный код сбоя и выпускать исправление после повторной экспертной проверки.
5. Ежемесячно пересматривать доступность источников, задержки очереди,
   распределение ошибок и долю пропусков; изменения моделей и промптов фиксировать
   версией пайплайна и проверять на неизменном контрольном наборе.

## Ограничения измерений

Текущие оценки confidence и relevance — эвристики, а не вероятности. Сводка
команды показывает эксплуатационные показатели, но сама по себе не доказывает
качество бизнес-выводов. Для калибровки нужны экспертно размеченные материалы и
регулярная оценка на отложенных новостях. Пользовательские отзывы добровольны и
могут быть смещены к более заметным результатам.

## Масштабирование и сопровождение

- API хранит состояние сессий и заданий в PostgreSQL; web-инстансы можно
  масштабировать горизонтально. Перед увеличением числа API-инстансов локальный
  rate limiter нужно заменить общим лимитером на gateway/Redis.
- Worker захватывает задания через PostgreSQL `SKIP LOCKED` и lease-heartbeat;
  число worker-инстансов можно увеличивать независимо от API. Суммарное число
  соединений ограничивать размером пула и лимитом базы.
- Миграции запускаются до старта API. Выпуск проверять на совместимость схемы,
  затем развернуть API и worker; после релиза сверить health endpoint, ошибки
  очереди и quality-report.
- Новые отраслевые факторы и типы источников вводить через версионированные
  конфигурации/миграции, оценивать на контрольном наборе и экспертной выборке,
  а не менять веса напрямую на пользовательских отзывах.
